# PureAgent 独立研究：程序应提供能力，不能把调查变成填表

日期：2026-10-19（Asia/Shanghai）。独立研究者：`/root/agent_freedom_audit`。

审计基线为上一轮已归档的 `7a743e0cab5dedf31230a0c2bc316aa191a0e23d` 对应实现和研究记录。本报告仅研究 PureAgent；没有修改生产代码，没有安装 Agent 框架，没有开展新的整板电气审查。第 4 节的三个小探针实际调用了当时的本地函数，其余反例明确区分已有实验证据与设计推论。

## 1. 独立结论

**现有“真实事实可回查、按问题展开、缺资料局部影响”的方向应保留，但它还不够。还必须允许模型决定如何调查、如何分解问题、什么时候使用近似或条件分析、如何改变解释。程序应使这些决定可以执行和核对，不应预先规定唯一正确的调查路径。**

最强的反对意见是：若把防错实现成“先填全器件信息、先确定全部工况、先完成固定模型、先给出整改方案，然后才允许形成结果”，就会把资料的不完整性变成模型的填充任务。字段完整之后，物理真实性仍然没有得到证明。上一轮放宽了几个门槛，并不代表这个风险已经消失。

相反，把所有检查都交给模型口头解释也不成立。NC 分组被错误导通、分页尾项丢失、同一物理脚的争议不出现在网络视图中，都是程序可以直接避免的事实错误。模型自由度应增加在调查和解释上，不能靠改写原始连接获得。

这里建议的不是新的大而全规则库，而是一种可执行分工：**程序保证查到的是什么、算出的是什么；模型决定接下来查什么、怎样理解，以及现有证据支持多大的结论。**

## 2. 审计依据与已实现能力

本轮读取了 `README.md`、两份 2026-10-18 研究文档、2026-10-19 PCIe 主研究、灵活性审计、电气审计、原 Clay 调查及复核记录，并检查了 `pureagent/dat.py`、`calculations.py`、`report.py`、`cli.py`、`pdf_tools.py`。旧 V1 方案用于区分历史建议与当前实现。

当前程序已经提供的是原生 DAT 查询、PDF 搜索/整页/渲染、受限标量计算和报告筛选。它没有部署独立模型运行底座，没有实现整板自动任务调度、自动模型构建或自动条件继承。因此，不能将下文对固定调度、固定拓扑或完整模型的批评写成“代码里已经有这些功能”。有些是已复现的门槛，有些是下一阶段应避免的开发方向。

当前值得保留的基础包括：解析一次后复用、全部对象可枚举、摘要可展开、物理脚与原始网名保留、NC 不导通、局部不完整记录仍可调查，以及缺少无关封装字段不影响接线查询。这些能力让模型能够选择调查策略，而不是要求模型重新充当解析器。[项目入口](../../README.md)；[PCIe 主研究](20261019_pcie_flexibility.md)

## 3. 哪些程序约束有用，哪些应由模型因题判断

| 事项 | 程序应保证的含义 | 应留给模型的判断 |
|---|---|---|
| 网络查询 | 物理端点、网络身份、已知冲突、分页范围准确；省略对象能继续取得 | 哪条网与当前问题有关，何时扩大范围 |
| 库或资料不完整 | 已有记录仍存在；未可靠解析的内容不伪装成确定事实 | 缺失内容是否影响当前判断，是否需要补读或换一种证明方式 |
| 器件类别、脚名 | 原始值和来源可回查；提示标签不覆盖原始记录 | 根据上下文识别角色、复用功能和模块边界，允许重新分类 |
| 算术 | 表达式按公布的运算语义执行；错误与非有限数明确返回 | 公式是否适用、参数怎样解释、是否可以用约束或近似代替完整工作点 |
| 条件计算 | 不把条件量包装成已确定的实际工作点 | 在相同条件下继续推导；比较不同场景；寻找对未知量不敏感的结论 |
| PDF | 文件有效、页码明确、文字与图像能回读 | 哪张表适用、是否需要相邻页、脚注或视觉检查 |
| 报告 | 确认、未确认和未完成不能混同；已取得的来源可回查 | 当前证据能确认什么，结论是否需要缩小，整改是否已有足够依据 |
| 运行资源 | 合理的上下文、计算资源和执行边界；中断后保留已完成工作 | 在预算内分配调查深度，合并/拆分任务，改变查询顺序 |

把物理脚号当字符串、把网络身份解析清楚、明确分页和运算语义，是可靠接口。要求每个元件都填 `MPN`、统一 `pin_direction`、完整 `min/typ/max` 或某个固定模型，则是在替模型预先决定调查所需的语义。前者可严格校验，后者没有全板通用的必填理由。

## 4. 反例：现有方向仍可能怎样成为枷锁

### 4.1 “条件值不能传播”会禁止合理的连续分析

基线 `calculations.evaluate()` 对条件计算返回 `trial_result` 和 `usable=False`，这是有用的区别；但同时返回 `trial result must not be propagated`。实际探针用已有 Clay 的名义设定关系 `58.5 × 1.3 / 7680` 得到约 `0.00990234375 A`，同时出现这一绝对禁止文案。

如果任务是在同一组明确假设下比较某种 PWM 策略，模型完全可以继续使用这个名义设定关系；但它不能把结果说成板上已经测得的实际电流。禁止一切继续使用，会迫使调用者把多步计算挤成一个大表达式、手工重新输入数值，或把状态改成 `valid` 才能继续。这些做法都没有提升证据质量。

应限制的是**丢掉条件以后升级结论**。同一场景中可以继续计算；在另一个场景中，需重新建立有关条件。也可能通过比较或上下界证明：最终结论根本不依赖某个未知量，此时可以缩小或解除相应条件。

反作用也必须承认：仅仅改一句文案并不会实现条件继承。当前工具不追踪条件依赖；后续调用若只复制数值而不保留场景，仍可能制造错误。阶段性的可行做法是保留相关计算引用及条件说明，由调查和复核核对，不先建设整板形式化状态系统。[计算工具](../../pureagent/calculations.py)；[原 Clay 核算](20261018_real_chain.md)

### 4.2 “确认错误必须给整改建议”把诊断和设计绑得过紧

实际调用现有 `build_report()`：采用原 Clay 调查和独立复核记录，原来输出 1 条确认错误；只删掉该候选的 `recommendation`，其余接线、要求和复核完全不变，输出变成 0 条。

这只是呈现门槛的探针，未改变原板，也未重新证明该错误。然而它清楚说明：程序把“已有足够证据确认问题”与“调查者已经写出整改方案”绑在了一起。

真实设计中，确定两个端口违反接口约定，未必能马上决定改接线、改器件、改供电还是改固件。整改取决于更多设计目标。此时应能报告已确认的问题，建议有依据则附，没有则省略。用一句空泛建议满足字段，或者为了填字段猜一个替换型号，都没有必要。

整改建议改为可选也不意味着它可以不受核对：一个正确的错误结论，不能自动证明随附整改方案也正确。现有 `report.py` 会复制候选里的建议，程序没有自动验证方案的物理适用性；应按其实际证据写作，不用新增“整改审批”结构补偿这个边界。[报告工具](../../pureagent/report.py)

### 4.3 完整对象清单不能变成形式上的全板覆盖

基线 `build_report()` 接收调用者提供的 `investigated_count`、`total_count` 和 `full_board`。探针传入 `1/1`、`full_board=True`，并在 scope 中明确写“只检查一条连接断言”，仍返回 `completed_review`。

这个行为不等于程序已经按器件数强制调度：当前没有调度器，代码也明确说计数和范围由调用者声明。它说明的是，**完成状态本身不验证覆盖范围**。不能将这个字符串或计数拿来证明全板电气覆盖。

后续若把“每个器件至少点名一次”用作完成标准，模型可能为清单打勾而做浅检查，遗漏跨器件问题。反过来，如果每个器件必须通过完整电气模型，又永远做不完。一个器件可能参与供电、复位和信号三个任务；一个接口任务可能覆盖几十只无源和连接器。

清单适合防止对象从系统中消失；短任务记录适合恢复工作。电气审查范围则应用实际做过的问题表达，例如“已核对 PCIe1 的 lane0 连接及选定侧带条件”，不能将对象访问次数替换为语义覆盖。无需为所有潜在错误建立穷尽矩阵。[原 Clay 范围记录](../../runs/20261018_clay_r6/original/investigation.json)

### 4.4 “全部无源随有源”也可能成为新的固定调度

“普通无源通常共享电路核算”是效率建议，不应升级为“无源只能附属于有源任务”。OpenCellular 选定 PCIe 信号是连接器间转接，本板没有对应收发器；只从有资料的 IC 发任务，就可能漏掉整段接口。J401 的 C65/C66 则更适合在同一差分路径任务中共同核查。

进一步说，“按功能块”也不能硬要求唯一分组。OpenCellular 的 J3314 同时带 PCIe、UART、IRQ 和同步信号；将整个连接器强制归入唯一类别会污染检查范围。一个边界对象可以被多个任务引用，模型可先给暂定角色，见到新证据后改组。[独立 PCIe 电气审计](../../research/20261019_pcie_audit/electrical_audit.md)

### 4.5 “缺少事实不猜”不能被误解成“未知就不许推理”

J401 的 DAT 没有导出若干电阻的 DNP 标记。这个事实禁止把它们默认成已焊，也禁止默认未焊；但不禁止模型分别分析两种装配场景，或先完成不受装配影响的连接核对。模块内部上拉同样允许通过适用资料补充解释，无需先把整块模块展开成新网表。

网名、`RSVD` 标签、`TX` 字样、典型参数都可以帮助提出候选假设和找到应读的资料。禁止把它们单独升级为最终事实，不等于禁止使用它们作为调查线索。

另一个反例是已经有依据的边界约束：若能证明某未知支路只会吸收电流，某项上界判断可能不需要其完整 I–V 曲线；模型应有机会证明这种关系。这里“只吸收电流”本身仍需依据，不能把任意未知器件直接当成这种负载。灵活性来自选择较小但足够的论证，不是忽略未知。

### 4.6 “只显示确认错误”不能使用户的问题消失

默认错误列表不应包含大量“型号未找到”提示，这一要求应保留。但如果用户具体问“这个接口能否达到指定代际”，而代际、模块版本或插卡条件决定答案，系统不能只回“0 个错误”。它需要如实回答这个问题尚未判定，并尽可能完成其他已经可做的核查。

一个简短的范围说明，以及确实会改变当前结论时的一次针对性询问，可能比让模型无限检索或默选代际更实用。不要因“不打扰 EE”的目标，写出绝对禁止提问的提示词；也不要把允许提问变成“先填写完整设计表”。是否询问，应看现有证据、用户任务与问题的重要程度。

### 4.7 只提供窄算术工具，也会限制模型选择正确方法

当前算术器适合小型标量表达式，本身没有义务变成所有工程数学的解释器。但以后若只把这一工具暴露给模型，再要求解决二极管工作点、容差组合或复杂反馈问题，模型就可能被迫用口算、重复线性近似或伪造一个“已知电压”。

应允许按实际问题调用已有的数值工具，或在受限工作区写小段可回放计算代码，再返回计算和适用范围。是否需要求解器由问题决定，安装一个框架也不会自动提供正确器件模型。资源与文件边界可以由程序控制；算法、分析顺序和局部近似应允许模型选择。这是后续能力建议，本轮没有新增执行工具或非线性求解器。

### 4.8 程序不懂一种格式，不应同时剥夺模型读取原文的能力

当前 `ToolSession.__init__()` 首先调用 `DatGraph(dat)`。图构建失败时，工具会话不能创建；CLI 返回未完成并退出。因此在这个会话入口里，连原文、已给定 PDF 及与图无关的算术都不能继续使用。这个调用关系是本轮代码审计的观察。`pdf_tools.py` 和算术模块本身可以独立使用，当前外部会话也另有文件工具；不能因此误称“所有资料阅读能力都被删除”。问题在于未来独立运行底座如果只暴露这个入口，就会继承同一个启动门槛。

建议在下一阶段把只读原文/PDF 能力与可靠图的构建成功分开。图不可用时明确返回不能提供规范化连接结论；原文仍可供模型定位局部记录、调查格式问题或核对不依赖该图的资料。模型发现一个可解释片段，并不等于已经恢复全图，也不应把手工猜测静默填回正常图查询。

这一改进比继续堆型号或电气规则更优先：它直接决定模型能否在程序遇到未覆盖输入时继续做有依据的工作。实现可以只是解耦会话入口和显式工具可用状态，不需要马上建设通用格式恢复系统。这仍是未实现建议，本轮没有放宽图解析成功的含义。[会话入口](../../pureagent/cli.py)

## 5. 本项目明确不应该做的事情

下面是开发取舍，不建议直接复制成每次调用都要阅读的长提示词。

- 不用字段填满程度代替证据充分性；不要求全板 MPN、封装、装配、工况先齐全。
- 不从网名、库脚名或典型值直接写入实际电压、方向、装配和器件功能；这些信息可以用于形成和检索假设。
- 不为了让图连通而短接电容两端、合并有歧义的网络、删除未知端点或猜物理脚号。
- 不预设每器件一次 Agent、只查有 PDF 的 IC、固定两跳、唯一功能归属或所有元件同一种模型。
- 不把原资料不存在的内容定义成必须抽取的字段；也不要求所有任务按固定的阅读、提取、建模、求解顺序执行。
- 不把同一问题的无限重试、更多 Agent 或更长检索当成获得缺失事实的办法；停止时保留范围和已有结果。
- 不把“报告字段非空”“两个名字不同”“返回 usable”当作证据已经被核实；也不再用更多自报字段伪装认证。
- 不把所有工程经验固化为强制规则。典型应用和参考电路可以提供候选方案，其适用性仍需判断。

其中禁止篡改接线、隔离 NC 等规则由程序直接实现；避免臆测和选择论证方法更多依靠模型行为、工具反馈与实证评估。两者不能靠同一套非空字段检查完成。

## 6. 模型需要拥有的具体空间

在现有事实工具之上，模型应能自主完成以下动作：

1. **形成并撤销解释。** 先判断一组网可能是 PCIe，经资料发现连接器的观察方向不同后调整解释，原始脚名和接线不动。
2. **选择更小的充分调查。** UVLO 单端点接线可直接核对，不必先处理 `boundary(['U6'])` 中全部 197 个外部端点。实际负载计算则可扩大到相关支路。
3. **建立和比较场景。** 将 DNP、外部输入或运行模式作为明确条件，分析结论是否随条件改变；无依据时不替用户选一个场景。
4. **选用恰当计算。** 根据问题采用直接比较、名义关系、区间、分段或数值求解；计算不是每个器件必经的仪式。
5. **选择下一份证据。** 文字不足时看图，型号差异影响结论时查版本，表头跨页时补下一页，同型号资料可复用。
6. **调整任务和表达。** 合并共享核算、拆开互不依赖问题，必要时交给子代理；将“整板会损坏”缩小为已经能证明的具体连接冲突。

允许这些动作，并不意味着所有解释都应永久进入事实图。暂定解释可以先留在调查笔记；只有需要复用或报告的部分再留下相应来源和条件。无需提前设计一套覆盖全部器件、模式与事实审批的结构。

## 7. 一手资料验证：现成 Agent 方法支持哪些边界

以下资料于 2026-10-19 实际读取。它们支持 Agent 工具与工作流设计方法；不能代替本项目的电气真值，也没有证明 PureAgent 的实际准确率或效率。

| 一手来源 | 实际支持的方法 | 对 PureAgent 的推论与限制 |
|---|---|---|
| [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 从简单方案起步；任务不能预先分解时由模型动态委派；运行中用工具结果获得反馈 | 电路调查顺序可以动态决定；仍需能回到 DAT、资料和计算。不是每次都应建多 Agent 工作流 |
| [Anthropic：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) | 工具应支持多种成功策略；验证器不应因无关格式拒绝正确结果；精简响应可保留详细入口 | 精简图视图与完整可查事实可以并存；评估应检验结论而非固定调用顺序。这篇文档也支持严格、清晰的工具输入语义，不能解释成取消接口约束 |
| [Anthropic：Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 避免脆弱的 if/else 提示词，也避免过分空泛；用代表性例子和按需检索组织上下文 | 不把每次新板异常加成永久提示词分支；保留能重新取证的路径，并用真实失败调整最小指导 |
| [LangGraph：Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents) | 区分固定流程与动态工具循环；Agent 可决定方法，开发者仍定义工具和行为指导 | 可用简单循环承载调查，局部确定性操作由程序做。不必因为采用 LangGraph 就画出全套固定电气状态机 |
| [Deep Agents：Subagents](https://docs.langchain.com/oss/python/deepagents/subagents) | 子代理适合隔离复杂任务的上下文；简单单步、需要连续中间上下文或开销过大时不适合 | 适合独立资料审计及复杂接口调查；不支持“每只电阻固定启动子代理”这一做法 |
| [Deep Agents 开源仓库](https://github.com/langchain-ai/deepagents) | 支持自定义工具、文件访问、上下文管理及可替换的组成部分；工具与执行环境承担真实边界 | 可以复用已有运行能力，不应为框架默认值硬改电路任务。这里没有安装或运行该框架，也没有把其能力当作本仓库已具备 |

这些来源的共同启发是改善模型可使用的环境与反馈。它们没有给出一套可直接照搬的 EE 检查规则，也不支持“使用 Agent 就不必检验输出”。

## 8. 对本轮两项最小纠正的独立意见

协调方已实施两项最小修正：调整条件计算的绝对禁止传播表述，保留条件结果区别；整改建议有依据才附，不再作为确认错误的前提。独立研究者已只读回查最终函数及保存的修改后探针，并在内存中重新执行这两项窄复核：条件结果仍为 `trial_result` / `usable=False`，说明要求调用者保留条件；删除原 Clay 建议后仍返回一项确认错误，且没有补出建议字段。确认所需的接线、要求和独立复核门槛仍在。**这两项修正有明确的已复现依据，未通过增加新必填字段实现。**

需要同时把边界说清楚：

- `trial_result` 与 `usable=False` 可以继续表达“尚未建立实际工作点”。允许同条件后续推导，不应被写成自动条件追踪已经实现。
- 下游若引用条件数值，需要保留影响结果的条件；若条件不再必要，应说明缩小结论或解除条件的理由。不要求所有无关假设永久附带。
- 缺少整改建议不应删除已经确认的错误；下游呈现也不应假定建议字段必定存在。
- 存在整改建议不等于整改已被验证。报告不应因为错误结论得到确认，就把未经核查的具体改值或换料写成确定方案。

协调方保存的 [修改前](../../research/20261019_agent_freedom/before.json)、[修改后](../../research/20261019_agent_freedom/after.json) 探针显示：只删除原 Clay 整改建议时，确认数量由原来的 `1 → 0` 改为 `1 → 1`；合成同条件分析中 `5 mA → 25 mW` 的数学值及条件标签保留，条件由调用者显式带入。`completed_review` 的调用方声明机制没有更改。

本独立报告不修改生产代码，整体回归结果由同轮主研究记录报告。其他较大的建议先保持为设计取舍，避免一次研究就增加新的调度框架、条件求解系统和覆盖数据库。

## 9. 下一阶段怎样判断方向是否正确

优先用真实输入上的行为判断，而不是用规则条数、字段完整率或 Agent 数量判断。

可保留少量能够翻转错误结论的对照：删除与结论无关的元数据后仍可完成；添加相关未知支路后不再假定无负载；调整组装条件后只有依赖它的判断变化；更换正确的资料查找顺序不会被拒绝；有足够接线与要求证据但无整改方案时仍能呈现错误。已有 Clay B/C、J401 DNP、OpenCellular 转接板及 NC 回归提供了起点。

运行底座接通后，再观察模型是否反复补字段、是否以错误状态绕过工具、是否因窄工具口算复杂问题、是否把阅读清单当成完成检查。记录实际判断结果、无效重试、工具失败、耗时和模型上下文成本；不能用少了几行 JSON 推导一个尚未测量的加速倍数。

既要测错误是否能检出，也要测合理的不确定结果能否保留、不同正确路径是否被接受。样本应包括能直接决定的接线问题、依赖外部工况的问题和没有确认错误的正常局部电路。不要因为样本零错误就强制 Agent 继续找出一个错误，也不要因它输出谨慎文字就自动认为研究充分。
