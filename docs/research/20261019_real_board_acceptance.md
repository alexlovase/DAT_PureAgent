# PureAgent 两份真实板卡的验收与调度选型方案

日期：2026-10-19。目标用户：资深 EE 工程师。状态：可执行的测试设计，尚未使用用户手中的两份新网表运行。

## 1. 本次要决定什么

主对照是用户 Windows 工作区 `C:\project\DAT_PureAgent` 中的 `planner_version=1` 与 `planner_version=2`。本地能力、版本和实现差异依据用户提供的对照说明，本次未读取该 Windows 工作区。两份新网表和对应 datasheet 尚未在本会话提供。

本 GitHub 仓库是另一条工具原型与研究路线，不具备等价的模型运行底座，不作为第三个全板参赛版本，也不代表本地 GitLab 实现已同步本文件。

此次验收回答四个问题：

1. 最终交给 EE 的确认问题，是否有充分、适用的工程依据？
2. 已知且当前输入足以判断的重要错误，能否稳定发现？
3. 缺资料、特殊连接和规则未覆盖情况，是否仍允许有价值的调查继续？
4. EE 为准备输入、判断报告和处理中断付出的时间，是否减少？

程序自己的义务完成率、目标脚计数和 blocked 数，不作为电气召回率。测试用的参考答案和验收字段只在评测后台使用，不成为模型运行前的新必填表。

## 2. 先隔离公共工具缺陷，再比较调度

保留现有版本快照与实际默认配置，避免比较过程中失去回退依据。不要用统一的包版本号 `1.2.0` 识别实验；后台同时记录代码提交、planner、parser、提示词配置、模型版本与资源上限。

根据用户提供的差异，先建立两条低成本确定性回归，并把修复用于双方公共工具基线：

| 已知问题 | 验收行为 | 不足以证明通过的检查 |
|---|---|---|
| Clay 的 NC 声明物理脚遗漏 | `AE1.2`、`AE2.2` 均存在于物理脚集合；NC 不并成普通导通网络；普通网络端点保持正确 | 只比较 548/546 或普通端点总数；总数相同仍可能脚号或归属错误 |
| 未参与运算的未知参数阻断计算 | 真正不在表达式及工具语义依赖中的未知参数，不影响可计算结果；实际所需未知量仍须明确处理 | 删除全部参数校验，或把未知值当零 |

537 个普通端点、548/546 个物理脚是用户提供的 Clay 对照数据，不是两份新板卡的预期计数。新板卡应分别建立自己的原始事实基准。

保留本地已有的单位校验、线性求解、求根和区间能力。工具回归检查使用外部已知关系、原始记录和人工核对的少量集合，不以被测解析器再次导出的内容给自己作证。条件计算可以继续推导，但需保留相关假设；未知温度等如果实际影响所用模型，就不能算作“无关参数”。

公共工具修复前的结果可作历史记录；以共同修复后的工具基线比较 planner，才能把差异较清楚地归因到调度。若两者确实无法共享同一工具层，先做实际产品对照，并明确它比较的是整套系统，而非调度的因果效果。

## 3. 输入材料与独立参考答案

### 3.1 输入不要求完整器件档案

每板先提供原始网表和已有 datasheet。必要时附一页以内的设计场景说明：已知供电范围、当前要验证的接口或负载目标、与当前问题有关的装配或外部模块信息。只写已知事实，缺失内容保持未知。

不要要求先填写全板额定值、精确封装、全部型号后缀或所有工作模式。若某个预期错误必须依赖一个板级工况，该工况应存在于提供给系统的材料中；测试作者不能在私有答案里知道它，再惩罚 Agent 没有猜到。

资料需要能区分适用型号、封装或引脚变体、文档版本与相关条件。型号相近不保证参数适用。典型值、保证范围、绝对最大额定值和推荐工作范围分别解释；“超出保证范围”不能自动改写成“必然损坏”。

### 3.2 建立少量工程问题的参考答案，不给每个器件填表

每板先人工选若干与实际使用目标和已发生失败相关的问题。覆盖重要电源/接口/模拟关系、正常情况及资料不足情况即可，不规定每板必须包含某种器件。

每个参考答案建议只记录以下信息，能用短段落表达时不强制结构化：

| 信息 | 内容 |
|---|---|
| 工程主张 | 在哪些已知条件下，哪个连接或参数违反/满足什么要求 |
| 证据 | 原始连接、适用 datasheet 条款和必要计算或工程解释 |
| 可判定性 | 此次提供给系统的材料是否足够判断；若不足，缺哪个关键条件 |
| 可接受结果 | 确认问题、该项有依据地无问题、或限定范围的信息不足 |
| 重要程度 | 误报或漏报会给 EE 带来什么实际代价 |
| 适用范围 | 只判断这个问题，不声称该板其他部分正确 |

参考答案不包括预期义务 ID、规则 ID、Agent 数量、固定工具顺序或唯一公式。模型可以使用其他成立的方法。

原板不自动标为“全板正确”。先人工审阅少量重点，再把所有被测版本的报告取并集、按工程根因归并后盲审。未列入初始答案的新发现应补审；确认后更新同一版参考答案并给所有版本重算。另抽查少量未被任何版本报告的高价值关系，防止双方一起漏掉的问题完全不可见。未审阅的其余部分仍是未知，不进入整板召回分母。

条件允许时由另一位 EE 复核争议和高代价结论。只有一位 EE 时也可以启动，记录判断依据和争议，不将产品内三个角色的共识当成独立真值。LLM 可帮助匹配报告、整理证据，不能作为本次唯一裁判。

## 4. 样本分成五类

以下数量是小规模起步建议，不是新的覆盖义务。可从 2 份原板、约 6 个错误变体、4 个正常局部对照、4 个等价变体、4 个信息退化用例中选择约 20 个有辨识力的案例；有重叠或不适用时减少，不为凑数造题。大部分案例可在工具层或局部调查层执行，不把全部案例都做成三次整板运行。

### A. 原始真实板

保留实际导出习惯、无用字段、重复器件、模糊型号及现有资料状态。用正常的整板检查请求启动，观察有效发现、报告噪声、关键未知和 EE 操作负担。

### B. 经 EE 证明成立的错误变体

从副本生成，每次优先改变一个工程根因。例子只在实际电路和资料支持时采用：

- 把输入连接到已知会违反适用电压范围的电源；不能只凭网名推断电压。
- 在已知实际用途和电流路径下改变二极管方向；不能把“方向看起来反了”当通用错误。
- 修改分压或反馈参数，使已有工况下的输入越界；核对负载、偏置、容差等是否影响结论。
- 改变已知适用接口的必要连接或元件；不要泛化“所有 PCIe 某位置必须有同一种电容”。

错误必须在本次提供的材料下可证明。保存改动清单、原有正确/可接受行为与预期根因；独立核对变体实际产生了该改变。一个根因可能引起多个后果，不能要求一定只输出一条症状，也不能靠症状数量虚增命中数。

至少选择少量关键变体作为完整网表输入，隐藏修改位置和答案，使用中性文件名及同一整板用户请求，测试自主发现。其他变体可以直接指定局部问题，以较低成本测试调查与数学能力。这两种结果分开统计；提示了目标脚后找到错误，不能算成调度发现能力。

若还提供原理图或设计 PDF，修改网表后应同步相应设计材料，或明确本次变体以哪个版本为准。器件 datasheet 通常无需改变。故意保留不一致材料时，将用例归为资料冲突处理，不能按无歧义电气错误计分。

### C. 经 EE 确认的正常局部或近边界对照

每类错误尽可能配一个适用条件下的正常/允许情况，防止系统靠固定模式报警。可以选择明确允许的极性或引脚复用、符合条件的工作区间、模块内部已提供的接口功能等。原板未经审查的其他部分不能因此标为无错。

边界对照先明确容差、工况及要求是否包含边界；不要因浮点显示或四舍五入差异误判。正常例同样需要可判定的依据，不以“板子以前能用”代替论证。

### D. 真正等价的输入变换

例如格式允许的记录顺序/空白调整，以及确认仅用于存储、不会改变连接或语义的内部标识变化。预期是相关工程判断相容、无新增虚构错误；不要求报告字句、任务划分或工具轨迹完全相同。

对有限预算的自主发现，相关结论差异是需要调查的稳定性信号，先复现和检查输入是否真等价；不是一次不同就否定架构。针对已指定的同一局部问题，能够设置更明确的结果一致性回归。

不要把电源网名、装配状态、型号后缀或额定值的删除一概当作等价变换。这些信息可能直接参与工程判断。

### E. 信息退化与冲突

| 变化 | 合格行为 |
|---|---|
| 删除与当前问题无关的封装/描述字段 | 当前可解问题继续；不把元数据缺失当电气缺陷 |
| 删除当前问题确实需要的额定值或工况 | 该结论局部保留不确定性，其他有依据的检查继续 |
| DNP 或外部模块信息缺失 | 可做条件分析；不擅自补装配状态或断言缺上拉 |
| 网表局部格式无法解析 | 展示受影响范围，可靠部分或原文入口仍可用于调查；不冒充全图已可靠获得 |
| 两份资料参数不一致 | 判断适用版本或保留冲突；不静默采用更方便的数字 |

关键预期同时包含“不凭空确认问题”和“没有把无关工作也停掉”。真正缺证据时的局部 unknown 合格；在已提供充分资料的案例里不必要地 blocked，仍是未完成。

## 5. 专门检验新版义务是否限制模型

从两板真实结构中选少量案例，不额外要求全板器件类型覆盖：

1. 一个可证明的问题跨越两个默认电路块，或一个连接器承载多种功能。模型能否扩大调查范围并给出有依据的结论？
2. 一个问题不在初始义务/规则清单里，但当前材料足以发现。能否创建、合并或调整调查，而无需伪装成某个旧规则？
3. 一个支路资料不足，另一支路有可确认错误。前者的依赖等待会不会无关地阻断后者？
4. 同类器件需要复用资料，但具体封装/后缀或适用条件不同。缓存是否减少机械重复，同时允许纠正绑定？
5. 一个普通无源可以随电路共享核算，一个关键无源值得深入。调度能否按问题处理，而不由位号类型一刀切？

预期只规定工程结果和重要失败，不要求使用某个预设扩展 API。跨块数据本身如果不可达，应首先定位数据/工具层；如果模型已提出有效问题却被义务约束拒绝，再定位调度限制。

## 6. 公平运行，区分两种比较

### 6.1 受控资源对照：比较调度的作用

尽量固定：输入及资料版本、模型和参数、公共工具、调查与复核角色条件、相同用户目标、整次检查的总资源上限、资料索引初始状态。

planner 专属提示词和内部拆分方法属于被测方案，不要求强行相同。不要把旧版的 6 个对象或新版的 8 个预估调用当统一预算单位；应使用可比较的整次检查耗时、总 token/成本等资源约束，并记录谁达到上限。达到预算上限后保留实际进展，不能显示为全板通过。

### 6.2 实际默认配置对照：比较产品体验

再用各自真实默认配置做少量整板体验对照，包含缓存、恢复和界面。默认配置对照与受控资源对照分开报告。更宽松预算换来的发现增加有价值，但不能写成“相同成本下调度更强”。不要求两种对照都全量交叉运行。

### 6.3 多次运行与隔离

- 先用 A 板或已有合成样本排除集成故障、验证评审方式。冻结候选后，先每板每版各运行一次，共 4 次，再在同一配置下累计到每板每版各 3 次，共 12 次原板运行，作为起步观察量。
- 正式比较只累计候选、输入与评测配置一致的运行。预跑若未触发相关修改且满足同样条件，可以计入；否则保留为调试记录，冻结后重新累计，不把修正前后的结果混成同一方案的成功率。若保留 B 为未见验收板，不用它做调参预跑。
- 每次运行都保留，不挑最好的一次，也不把三次发现并集当作单次能力。发布关心单次可重复性。
- 若关键结论摇摆，针对相关案例追加运行；不把全部变体、全部配置和全部次数机械相乘。
- 新运行隔离调查答案、历史结论和状态；同样版本的 PDF 索引可设一致的冷/热条件。真实恢复测试另行保留状态，不能混入“从零检查”的结果。
- 交错或随机运行顺序，记录异常服务失败。失败不能静默删除；区分平台事件、工具错误和模型判断，并报告是否重试。
- A 板可用于开发调整，B 板保留为冻结配置后的验收板。看过 B 板结果后据此调参，它就转成回归数据；两板都已大量调参时不要再称独立留出集。之后需要新的未见案例验证泛化。

已知错误变体中的少数关键案例应做隐藏位置的整板发现测试，其余可做局部测试。恢复、依赖失效和全局阻断问题必须至少有相应集成验证，不能仅凭 worker 单测宣称整条链路通过。

## 7. 评分逻辑：真问题、漏检和使用代价同时看

### 7.1 确认问题的可信度

按同一根因/适用条件/受影响关系归并问题，保留原报告供易用性评审。不同版本义务 ID 不影响匹配。

对最终确认问题进行人工裁定：

- T：工程上成立，且输出依据与条件足以支持。
- F：工程判断错误，包括把已知允许情况写成缺陷。
- U：待审或依据不足，后台再区分 `U_pending`（评审未完成）与 `U_unsupported`（评审已确认本次输出没有足够依据作确定断言）。

`U_pending` 需要补审，不能直接判假。`U_unsupported` 即使后来发现电路恰好确实有错，也不能自动证明原输出的论证合格；补充论证后的新报告应作为新结果评审。已归入 F 的问题可另外标记证据缺陷，不重复计入 U 的分母。

令 N = T + F + U_pending + U_unsupported。首先报告这些原始计数，以及严重程度、重复条目和 EE 驳回理由。当前合格确认项比例为 T/N；如果所有尚待评审项最终合格，可能上限为 (T+U_pending)/N。这个范围仅来自尚未完成的裁定，不是总体 precision 的统计置信区间。`U_unsupported` 单独保留为报告质量失败，不能从分母移除以提高数字。N=0 时无可评确认项，不记作 100% precision。

不要用“正常器件数”作为真负例分母计算整板 accuracy，数量巨大的正常无源会掩盖少量重要错误。数据缺失如果占据用户的电气错误列表，即使后台叫 warning，也按实际用户负担计入。

### 7.2 已知问题发现与恰当的不确定性

对于预先确认且此次输入足够的错误，记录每次是否发现、是否有证据、是否被错误过滤、是否被不必要 blocked。已知错误检出率的分母来自独立参考答案，不来自程序生成的任务。

原板已知问题、错误变体、指定位置的局部诊断分别报告。未能建立整板完整真值，就不声称整板召回率。

对确实不可判定的案例，正确限定范围可以通过该不确定性测试；它不是电气通过，也不抵消其他可解案例的漏检。全部 blocked 或空报告不能靠“没有误报”获胜。

### 7.3 EE 使用代价

| 指标 | 如何观察 |
|---|---|
| 输入准备时间 | 附加整理、填写字段、解释设计意图实际用了多久；测试作者一次性标答案的时间另计 |
| 无关中断 | 用户被要求补齐、确认、豁免了多少与当前关键结论无关的信息 |
| 首个可靠结果时间 | 有真问题时看首次可核实问题；无真问题时看获得诚实、有用的检查结果所需时间 |
| 审阅总时间 | EE 看完整份实际报告、打开证据、接受/驳回发现花费的时间 |
| 重复与噪声 | 同根因重复报告、泛化风险提示、缺封装/型号等无关提醒 |
| 恢复后的额外工作 | 中断后重复调查量、重复报告、重新要求用户输入的内容 |
| 机器成本 | 总耗时、总 token/成本、重复昂贵检索、资料上下文体积 |

不要只优化工具调用次数。一次长查询可能比多次精准查询更昂贵；独立复核重新读取必要原文是有效工作，不应被“同 PDF 只能读一次”规则禁止。资料缓存可复用解析结果，复核仍需真正查看本次相关依据。

报告内容盲评时隐藏版本标签、打乱顺序。易用性评审保留真实排版、重复内容和跳转体验，否则人为清洗会掩盖产品负担。记录学习顺序影响，不用第二次看同一块板更快来证明某版本更好。

## 8. 最小落地方式与模板

复用本地已有 SQLite、报告导出和运行轨迹，不需要先接入新的评估平台或重写 Deep Agents 底座。最小增加五个能力：

1. 以明确配置启动隔离运行，可选择 planner 版本。
2. 自动保存运行配置、输入版本、最终报告和真实工具事件。
3. 将运行报告与 EE 裁定记录关联，支持新发现待审。
4. 自动汇总上述计数、成本和中断信息；工程真值由 EE 判定。
5. 对同一案例并排查看两版本报告及相关原始证据。

输入校验和后台可复现标识自动记录；不把所有哈希、版本和轨迹都塞入模型上下文或 EE 主报告。实际两板材料和私有答案仅存放于用户授权的位置，本研究文档不上传其内容。

### 8.1 私有案例卡模板

```text
案例编号：中性编号（例如 case_017）
测试层次：工具 / 指定问题的局部调查 / 隐藏位置的整板发现
输入：原板或变体路径、提供给系统的资料和场景
对系统的任务：实际用户请求，不泄露私有答案或变体位置

仅评测者可见：
工程主张：
原文及适用条件：
本次输入是否足够判断：
可接受结果及关键错误：
重要程度与受影响范围：
若为变体，具体改动及独立确认记录：
```

可接受结果描述语义，不写死一套措辞或工具调用顺序。案例编号用于比对，不必在产品界面出现。答案文件应在被测 Agent 可读取范围之外；新运行不能看到旧报告、裁定记录或带答案的文件名。

### 8.2 一次运行记录模板

```text
自动记录：案例编号、运行编号、代码提交、planner/parser、模型与配置、
          输入/资料版本、冷/热状态、总预算、实际成本、开始结束时间、
          结束原因、报告路径、工具事件路径。

EE 裁定：确认成立 / 错误 / 待裁定的独立问题，已知问题漏检，
         证据不足的确定断言，重要未知是否妥善说明，
         输入准备与审阅用时，无关中断和重复报告。
```

这些是建议记录项，可从现有结构映射，不要求改变产品输出契约。测试汇总中允许数据暂缺，不能为了填满测试表推测耗时或真值。

### 8.3 评分伪逻辑

```text
运行并保存实际结果
  → 按工程含义匹配已知问题
  → 对所有新确认问题及争议进入 EE 裁定
  → 更新同一版参考答案，对所有候选一致计分
  → 分别输出报告可信度、已知检出、未知处理、EE 时间和机器成本
  → 对差异案例检查实际工具事件，定位原因
```

若两版本都漏掉隐藏位置的错误，再用指定局部任务诊断：局部能解而整板漏掉，调查入口/范围/预算值得检查；局部也不能解，继续查资料提取、工具能力、推理或用例有效性。此诊断提供线索，不单靠一次运行就认定因果。

## 9. 如何决定最新实现

不设一个没有样本依据的综合分，也不要求所有未知新能力挑战用例全部通过后才开发。区分已建立的核心回归与尚在探索的能力用例。

默认版本选择建议遵循以下顺序：

1. **确定性基础回归通过。** 原始连接事实、NC、实际依赖和数学语义等已知错误先修复。
2. **解决具体高代价输出失败。** 经复核确认的严重误报、凭空补值作确定断言、把必要未决项藏成“全板通过”，都应先定位修复再考虑默认升级。先排除错误标签、资料冲突和环境问题，不把一次偶发差异上升成普遍禁令。
3. **保持已知可解问题的发现能力。** 新版不能靠更少调查、全部 blocked 或过滤掉有依据的问题换取干净报告。对关键案例的差异复现并审阅轨迹；在既定预算下决定是否满足当前产品范围。
4. **呈现可重复的真实收益。** 更少 EE 审阅时间、更少无关提问、更快形成可靠结论或较低成本，至少一项明显改善；义务清单更长不算用户收益。

| 实验结果 | 版本选择 |
|---|---|
| 新版保留/改善已知检出和报告可信度，同时降低 EE 或机器负担 | 支持在已验证范围内升级默认，继续保留回退和真实运行回归 |
| 新版更便宜，但跨块问题被范围约束挡住 | 暂不据此替换默认；保留资料复用/预算优势，做一次放宽义务或边界的针对性消融，再验证 |
| 新版更少报警，但已知可解问题变成 blocked 或消失 | 不能当作精度提升 |
| 新版发现更多，但大量新发现尚未裁定 | 先完成裁定；新增条数不能直接证明收益或误报 |
| 两者差异很小或证据相互冲突 | 不因版本号更大强行切换；维持已知可恢复路径，补最有辨识力的案例 |
| 两者都出现当前范围不能接受的严重错误 | 两者均未达到该范围验收，不能因为其中一个更好就宣称可用 |

“保留新调度的缓存、稳定记录和预算管理，同时允许模型扩展义务”是值得检验的候选，不是未经实验就确定的最终混合架构。先让实际失败决定是否需要这个变体，不预先搭建第三套完整调度。

两份板和同板重复运行能够支持有限范围内的开发选择，不能证明对所有板型的泛化性能。报告 3/3、2/3 等实测计数及具体差异；不要将同板大量重复视为大量独立板卡，不凭少量零误报宣称总体 95% 或 99% 精度。

## 10. 建议执行顺序

1. 冻结两个本地候选与共同工具基线，补上述两个确定性回归。
2. 选 A 板做开发样本，B 板尽可能保留作冻结后的验收样本；整理已有输入，不补齐整板模型库。
3. EE 先标少量重要可解问题、正常局部和真正未知项；编写少量真实适用变体。
4. 用 A 板或合成样本完成集成预跑；冻结后启动 4 次原板基础运行，在相同候选和输入下累计到起步的 12 次。中途修改候选则单独记录，不能混算；用过 B 调参就不再称其为未见验收板。
5. 关键变体做隐藏位置的整板发现，其余按目的选局部或工具测试；对复现风险追加最少必要运行。
6. 盲审报告并集，抽查未报告的重点关系，记录 EE 时间及报告噪声；对所有版本使用同一版裁定。
7. 按具体工程失败与真实收益选择默认。把已经验证的案例纳入回归集，未解决新能力保留为能力测试。

这一方案的核心交付是能解释版本差异的一组真实证据，而非一套要求模型把所有器件填完才能结束的新工作流。

## 11. 独立审计与方法依据

本次由独立子代理 `ee_acceptance_audit` 审计设计，重点修正了：原板未知真值、未标注新发现、局部提示泄露、等价变换与信息退化混淆、blocked 刷分、不同拆分方式预算不公平、重复运行冒充独立样本等风险。它未读取 Windows 本地仓库，也未运行两份新板卡。

下列一手资料支持评估方法；本文件中的 EE 案例、数量、评分和选型方案是结合项目情况提出的设计，不是外部资料对 PureAgent 的实测验证。

- [Anthropic — Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：区分任务、重复 trial、轨迹和结果；代码、模型、专家评审各有适用处；允许有效替代路径，以真实失败建立能力与回归评估。
- [LangChain — Evaluating Deep Agents: Our Learnings](https://www.langchain.com/blog/evaluating-deep-agents-our-learnings)：按案例检查最终响应、工具轨迹及状态，结合低成本局部检查与完整运行。无须为采用这些方法强制迁移到新平台。
- [NIST — Confidence intervals for a binomial proportion](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)：少量样本或少量失败时，观测比例不足以直接证明总体性能。两板重复的相关性还限制了简单二项推断的适用性。
- [PureAgent 当前开发原则](../PureAgent_Design_Principles.md)：程序保持事实与工具语义可靠，模型保留假设、调查范围和分析方法的调整空间。
