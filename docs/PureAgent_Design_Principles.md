# PureAgent 开发原则：让程序支持模型调查

更新：2026-10-19（Asia/Shanghai）。适用于后续实现选择；历史 V1 方案按本页及后续真实实验解释。本页是开发方向，不是新增的运行必填表格或审批流程。

## 1. 核心分工

**程序维护可回查的输入事实，提供可靠、易组合的工具；模型根据当前问题组织调查、选择方法、解释证据并修正判断。** 程序的作用是扩大模型能够有效处理的问题范围，减少机械操作和无关上下文。

真实输入、器件组合和工况无法预先穷举。模型能够提出、比较和放弃假设，按需阅读原文、采用等效关系或上下界、调整调查范围。这些能力应有工具支持。

| 事项 | 程序承担什么 | 模型保留什么判断空间 |
|---|---|---|
| 输入事实 | 保存明确的实例、物理脚、网络和原始出处，显示局部冲突及无法解析处 | 解释标签、辨认导出差异、提出局部适配或待验证映射；不会因此覆盖原始事实 |
| 工具执行 | 正确查询、分页、搜索、读页、计算、缓存，清楚说明错误和能力范围 | 自主组合工具，跳过不必要步骤，尝试与问题匹配的其他分析方法 |
| 电气知识 | 可以提供有来源和适用条件的规则、器件知识及计算方法 | 判断适用性、比较不同解释、发现规则之外的问题 |
| 调查范围 | 提供完整可展开数据和进展保存，避免对象静默丢失 | 决定先查哪个电路、展开哪些支路、是否拆分任务，按新证据调整 |
| 对外结论 | 保留已经调查、独立复核的真实问题及其依据，表明实际范围 | 对证据作工程判断；建议有依据则附，不强迫给唯一整改方案 |

工具参数校验保护的是工具自身含义。例如计算器不能把未知数当零，网络查询不能把 NC 组当导通网。这些边界不应扩大成所有调查都必须先完成同一种模型或字段表。

## 2. 程序不应普遍强制的事情

以下列出的是会缩小有效调查范围的设计方式，不是声称所有项目里都不能存在相应功能。

1. **为开始工作而补齐整板资料。** 缺封装、型号后缀、装配说明或某份 PDF，按当前断言决定是否重要。已知不完整不等于所有工作都不可开展。
2. **把预设检查清单当成检查能力的全集。** 清单可以提醒常见问题，模型可以发现列表以外的关系，也可以说明某项不适用。
3. **把图构建成功作为阅读原文的前提。** 不支持某种导出时，应仍有独立只读入口供模型检查原始 DAT 和资料。局部调查不能冒充已经得到可靠全图。
4. **按每个器件、每个类型或固定跳数锁定任务。** 接口、电源、模拟电路、连接器都可成为入口；任务可重叠，普通无源通常随相关问题共享分析，关键独立问题可单独调查。固定裁剪不得隐去仍会影响结论的支路。
5. **把工具白名单写成唯一允许的工程方法。** 当前标量计算器只是已实现的一种工具。后续可提供合适的脚本、代数或求解器能力，模型在实际授予的执行范围内选择；不要求先建设完整器件模型库。
6. **禁止有条件的中间分析。** 模型可以做假设、上下界和多种情形的分析，继续推导时保留同一组相关条件。不能仅因为没有唯一实际工作点，就拒绝所有设计关系和局部计算。
7. **用无关的输出字段决定问题是否存在。** 能确认错误与能提出可靠整改方案是两件事。证据字符串非空、置信分数、调用次数、器件计数也不自动证明内容真实或全板已查完。
8. **把每个经验写成新强制分支。** 优先改进工具说明、真实示例和数据可达性；只有含义稳定、适用范围明确且经实际验证的部分才值得固定。复杂提示词中的大量 if/else 同样会成为脆弱程序。

## 3. 调查中允许不确定性，结论中保留其影响

模型可以说“先按这种可能情况试算”，然后核对假设是否自洽、是否适用；也可以比较几种情形，找出真正会改变结论的变量。假设是调查工具，不能自动登记为已经观察到的输入事实。

本次 J401 案例中，DAT 没有保留原图的 DNP 意图。模型可以分别分析某个上拉装配和不装配的情况，判断内部模块上拉与外部支路如何影响当前问题。它不需要为满足字段要求先猜一个装配状态，也不应要求用户补齐整个 BOM 才继续。

条件分析允许多步。例如在假定 5V 理想电源跨接 1kΩ 电阻的同一情形下，先算 5mA，再算 25mW。这两步始终带有原情形条件，不能只复制 5mA 而丢掉其来源和假设。是否能进一步确认错误，取决于适用要求覆盖哪些工况，以及现有证据能支持什么结论。

同样，求某个上界未必需要重建完整 I–V 模型；核对 UVLO 同网端点未必需要全板工作点；识别 PCIe 跨电容路径也不需要先证明所有高速电气指标。模型按问题选择足够的方法，结论限定在该方法能够支持的范围内。

独立复核集中在准备对外确认的问题上。调查过程中的每个假设、每个字段和每步算式不需要分别启动审批 Agent。程序记录真实执行来源，复核者回到相关原始依据；仅写两个不同角色名字不会自动构成独立复核。

工程错误列表仍只列确认问题；用户明确询问某个设计目标时，应直接回答已经能确定什么，以及尚未确定的关键条件，不能用空错误列表代替答案。只有确实会改变当前重要结论、且现有资料无法取得的条件才值得针对性询问，无关的封装缺失等仍留在内部。

## 4. 规则、工具和上下文如何增长

**可以建设可复用的电气规则和模型。** 避免强制齐全，不意味着每次都由模型重做已知工作。稳定的单位处理、成熟求解器、明确接口规则和已验证计算都有价值。它们应说明输入、适用条件及局限，模型能看见依据、组合使用，并在不适用时调整调查。

新增约束前，工程判断应落到三个问题：它修复了什么实际失败？限制的是工具自身语义还是本该按情境决定的分析？一个合理的替代方法还能否完成工作？这些问题用于设计讨论，不增加新的模型输出字段。

上下文以当前相关信息为主，保留检索和展开入口。需要完整枚举时由程序支持，不让模型反复阅读整板重复路径、哈希和所有资料页；也不采用无法恢复尾部对象的摘要。来源和缓存标识由程序保留，模型只需获得当前使用的可回查引用。

进展描述应区分已看到哪些输入、实际调查了哪些关系、有哪些重要问题仍未确定。程序返回的完成标志只是执行声明，不能替代电气覆盖证据。运行预算可以配置；到达边界时保存进展与范围，不把预算耗尽标为全板通过。

评价模型时关注真实任务结果和原始工具记录：有无凭空补事实、遗漏重要支路、不必要的停机、确认错误丢失或无关上下文。允许不同但成立的调查路径，不以是否严格重复某条参考工具顺序衡量成功。样本和反例用于发现问题，不能被宣传为已经穷尽现实。

## 5. 本轮已落实与后续优先项

本轮沿着两个已复现的具体问题做了最小修正：

- `calculations.py` 不再指示条件试算完全禁止继续使用。它允许在同一明确条件下继续分析，仍将结果放在 `trial_result`，不升级成实际工作点。**自动条件继承未实现**，由调用者保留相关情形。
- `report.py` 将整改建议改为可选。实际连接、适用要求、错误说明和独立复核保持；已确认的问题不会因暂时没有可靠改法而消失。已有建议保留，但该呈现工具不会独立验证建议本身。

当前 `ToolSession` 仍先构建 `DatGraph`，失败后不能提供该会话内的原文和 PDF 查询；这是优先需要解耦的后续入口限制。本次会话通过外部文件工具开展研究，不等于仓库已经具备这种后备入口。

后续优先提供独立原文读取、易组合的分析执行能力，以及模型可调整的局部任务组织。自动条件传播、通用脚本/求解器入口和独立模型 API 底座都还没有实现。本轮没有新增一套场景审批框架，也没有测量 LLM 编造率、整体性能或全板召回率。
